# PM Server 使用指南

分享仅提供使用分享内别名的任务进度、优先级与依赖。真实名称、标题、正文、日志、附件、运行身份和本机路径不向访客开放；分享 CSV 和详情由受限数据模型重新生成，不能下载原始文件。通知正文使用通用提醒，详情通过已授权的本机工作台或 CLI 查看。

## 待确认任务跟进

此功能属于 GitHub Unreleased 源码，已发布的 npm `0.1.0-rc.16` 包不包含此功能。试用需使用经审阅的源码候选，安装现有 npm 包不会获得此功能。

后台监测独立巡检已确认登记项目中的 `待确认` 任务，不要求有进行中任务、执行路由或运行观察。按 `project-manager.config.json` 当前登记经理跨项目合并到期卡片，不使用任务行中的旧经理路由；无经理时报告诊断，不猜收件人。

默认首次一小时后提醒（`PROJECT_MANAGER_CONFIRMATION_AFTER`，秒，最小60），接受后一天再提醒（`PROJECT_MANAGER_CONFIRMATION_REPEAT`，最小3600），失败或停用后五分钟重试（`PROJECT_MANAGER_CONFIRMATION_RETRY`，最小60）。每代最多三次快速失败尝试，之后使用每日重复间隔；接受后重置该预算。冷却期间健康仍保留失败与未知投递计数。变量配置在监测进程环境。缺失、坏或未来时间从本机首次发现计时；任务行、详情或经理变化，以及观察到离开后重入，开启新等待间隔。两次巡检之间的变化无法重建。私有应用状态持久保存冷却，并以投递锁防并行重复。

通知采用固定通用正文，经理通过授权本机工作台或 CLI 核对等待谁、问题或证据、确认后动作和跟进时点。后端接受不代表经理已处理或真实宿主唤醒；不改任务真源、不重派、不自动催用户或恢复暂停。活动任务的限时监测暂停不静音此独立分支，受阻及用户暂停任务不纳入。移除项目或明确停止监测后不再巡检。服务健康中的 `confirmationWatch` 显示覆盖数量、冷却、失败及固定诊断码。发送中断保留 `UNKNOWN` 并等待重复间隔；外部已接受后进程崩溃不保证严格只发送一次。


## 当前版本

`0.1.0-rc.16` 为已发布的预发布包。使用 `npm install -g pm-server@0.1.0-rc.16` 固定版本以便复现；`next` 跟随注册表标签。GitHub Unreleased 源码改动与该已发布包分开。

| 能力 | 范围 |
| --- | --- |
| 多项目工作台 | 已有功能迁入，包含认证、登记、分享与时间轴 |
| 监测与提醒 | 任务真源只读，运行记录保存在应用状态目录；通知后端须显式配置 |
| 通用事件入口 | Codex、Claude Code、DSH 可使用同一 JSON 接口，原生 ID 按平台和实例隔离 |
| Codex Hook | 显式安装并备份；必须在目标宿主核验信任与真实事件 |
| DSH | 最小 Cordis 观察器，只订阅三个生命周期事件；实际宿主重载待验证 |
| Claude Code | 可接入标准事件；原生 Hook 自动安装尚未实现，不宣称完整集成 |
| 操作系统 | 本轮在 macOS 验证；Linux、Windows 尚未验收 |

标准事件入口可用不等于平台已经原生接入。工作台显示的会话状态也不等于任务验收结论。

## 安装与使用

需要 Node.js 22 或更高版本。应用运行仅使用 Node 内置模块，不需要 Python；配套 Skill 的项目工具需要 Python 3.10+。

```sh
# 可选：从源码目录生成 tarball 并安装
npm pack
npm install -g ./pm-server-0.1.0-rc.16.tgz

# 从 npm 安装预发布版
npm install -g pm-server@next

pm-server doctor --json
pm-server setup
pm-server status --json
pm-server open
```

npm 安装只安装文件。首次启动由你选择，不会通过安装钩子修改宿主配置或启用系统自启。工作台默认 `http://127.0.0.1:9999/`，密码在应用状态目录的 `password.txt`，`status` 返回实际端点。

```sh
# 有效项目自动注册，无需在工作台确认
pm-server project request --repo /absolute/path/to/project
pm-server project list

# 停止两个后台组件并持久记录停用意图
pm-server service stop

# 查询不启动服务；ensure 仅在已有启用记录时生效
pm-server service status
pm-server service ensure
```

应用状态独立于 AI 平台。macOS 默认为 `~/Library/Application Support/pm-server`，可用 `PM_SERVER_STATE_DIR` 或 `--state-dir` 指定。测试必须同时指定独立目录与端口，例如 `--state-dir /tmp/pm-server-demo --port 10009`；不要用测试争用正式 9999。

`service run` 在前台运行工作台和监测，便于诊断。系统自启安装、自动升级和旧 project-manager 安装的数据迁移尚未提供；本版使用显式启动与停止。

## 首次启用 Codex 集成

安装后的接入引导主入口是 CLI 的 `pm-server setup`（0.1.0-rc.4 起提供）。在真实终端运行，菜单逐项显示已完成、待操作、待验证和暂不需要；可随时退出，再次运行时重新检测并继续。工作台负责后续状态查看和提醒。

```sh
pm-server setup
# 继续引导时使用相同状态目录及端口：
pm-server setup --state-dir /tmp/pm-server-demo --port 10009
pm-server setup codex --dry-run
pm-server doctor --check-host --json
```

菜单可安装/修复 Hook 并启动服务；安装前说明用户级权限和备份，保留其他 Hook。也可打开正常 Codex CLI，在其中完成登录、`/hooks` 审查信任和一次无害工具操作，`/quit` 返回后重新检测。引导不会自动授予信任。项目连接和通知后端选择可独立操作；后台首次发现已登记经理后自动检查通知通道，只有异常需要处理，可修复后重试。

选择 Codex 通知会把不含凭据的后端选择保存到应用状态目录，并保留实际端口和监听地址重启该目录的服务。后续终端及后台服务共享此选择；显式通知环境变量优先，有冲突时引导要求先调整环境。自定义后端见“配置提醒”。不会自动选择目标或发送测试消息。

自动化必须显式使用 `pm-server setup codex --json`：合并并备份 Hook、自动准备默认Codex通知通道并启动服务后返回 JSON 和未完成项，**不执行交互菜单中的其他操作**。非终端裸 `setup` 拒绝修改并提示正确命令。npm 安装仍只安装文件，不使用 postinstall 修改宿主或安装系统自启。应用状态目录绑定保存在用户级 Hook 旁，后续 Codex 无须继承初始化环境变量。

较早版本可用 `adapter install codex` + `service start` 分步操作。随后在Codex CLI运行 `/hooks`，检查并信任本次定义，再运行一次含工具调用的真实会话。配置安装不自动建立信任，应用不修改Codex内部信任库；升级后定义变化需重新核验。

`doctor`、`status`、`service start` 和 `setup` 分别报告Hook配置、缓存观察、宿主信任待核验和通知配置，不以工作台启动或缓存存在判定完整就绪。`ACTION_REQUIRED` 表示仍有接入/验证步骤。运行观察到位后仍须按“配置提醒”设置通知后端、登记经理和执行路由，并实测提醒投递；安装完成不等于遗漏回调兜底已经可用。

## 工作台基础检查与可选诊断

工作台可独立于AI宿主和经理会话使用。**设置 → 接入引导**的基础检查只关注项目来源可读性；来源无法读取时明确提示。已选宿主的必要接入配置有独立计数。Codex检查Hook回传定义、命令入口及状态绑定，以及可执行的通知发送后端；配置齐即可显示已配置，运行验证延迟。Hook加载/事件、实际投递/回传及经理对齐在折叠运行诊断中，不计初始未完成。引导不检查登录，无需经理在线即可查看任务。应用owner鉴权、分享权限、CSRF及来源隔离保持不变。

基础检查在初次加载、页面可见和可见期间每分钟更新。“重新检测”只刷新基础来源，不进行宿主probe或逐执行会话恢复扫描；“检查宿主能力”和运行诊断分别触发对应检查。界面显示检测中、结果或失败及最近成功时间。分享访客不能读取owner诊断或发送测试消息。

不同宿主使用独立页签。切换只改变展示，不保存范围、不探测宿主或发送通知；当前宿主的检查范围需勾选后明确保存，不会顺带保存其他页未提交的选择。全局来源检查和通用项目只读诊断留在外层，Codex本机观察恢复操作归Codex页。宿主选择仅控制管理/检查范围，不安装、卸载或启停Hooks、通知或会话。已保存选择优先；既有Codex绑定、已保存Codex通知或显式通知环境可作为兼容接入证据，单CLI安装不算选用。未保存时可用 `PM_SERVER_HOSTS=codex,dsh` 指定检查范围。DSH仅有生命周期观察适配器，未提供双向通知。

以下能力区分必要配置与延迟验证，均不锁工作台访问：

| 步骤 | 程序如何检查 | 未完成时怎么做 |
| --- | --- | --- |
| 安装运行观察 | Hook定义及应用状态目录绑定匹配 | 执行显示的安装命令；已有服务不必为此重启 |
| 信任与启用 | 通过Codex公开 `hooks/list` 检查当前Hook；不修改内部信任库 | 在Codex CLI打开 `/hooks` 审查并信任；被禁用时启用 |
| 真实运行事件 | 当前定义、脚本和目录绑定对应的Hook执行记录，须包含工具完成事件 | 运行一次含工具调用的会话再检测；通用缓存行不视为该步骤完成 |
| 经理与执行路由 | 当前登记与观察覆盖，不要求会话在线 | 已有经理在真实获授权管理请求中核对并修复可确认的路由；此前仍可查看任务 |
| 后台通知 | 后端已启用、程序可执行、参数是合法字符串JSON数组 | Codex接入后随服务启动自动准备；异常时点击“检测并连接通知通道”，自定义配置和显式停用优先 |
| 通知通道自动检查 | 后台首次发现已登记经理后自动发送检查消息，按当前后端和经理保存结果 | 成功无需操作；失败提示登录/经理可用性问题，可点击重试，无需识别会话编号 |

未知或不受当前Codex版本支持的检测结果保持“待验证”，不会显示为未安装或自动勾选完成。`doctor` 默认只做文件/状态检查；增加 `--check-host` 才通过公开Codex接口检测Hook加载/信任（不查询账号）：

```sh
pm-server doctor --check-host --json
pm-server status --check-host --json
```

同一Codex实例在完成Hook接入后的服务启动时自动准备通知通道，无需export配置。后台首次发现已登记经理后自动检查通道，默认每分钟发现新登记；无需选会话或确认收件，仅在异常时点击重试；兼容旧Codex任务账本中的原生UUID经理引用，不修改任务文件。跨平台或其他实例可按下方“配置提醒”使用自定义后端；显式配置及停用优先。CLI命令仅供自动化和高级操作：

```sh
pm-server notification test --manager codex:default:SESSION_ID
# 仅在目标会话确实收到后执行；这是你的确认记录
pm-server notification confirm
```

自动检查仅发送到已登记、与后端兼容的经理，不随意使用其他会话；每个后端/经理组合成功后不重复发送。失败最多自动尝试3次、间隔至少5分钟；不确定的中断不会静默重发。后台监测与检查使用同一投递实现；成功仅表示通知服务接受，不宣称实际收件或经理已处理，接入不再要求人工确认。以下手动测试/确认命令仅作为高级诊断保留。后端或参数变化会使旧验证失效；Hook定义、脚本或目录绑定变化后也要重新验证运行事件。检测失败会保留提醒并提供重试，不会因此更改任务状态或自动授予信任。

### Hook的权限、限制与备份

Hook按当前用户权限运行，可能在Codex对话沙箱之外执行。请先审查来源和脚本，再通过 `/hooks` 信任；安装器不会自动授予信任。当前观察脚本只记录会话运行状态与最小接入验证信息，不修改任务CSV或详情，也不保存提示词、工具输入、认证内容或会话全文。

需要可用的Node.js、正确且可访问的脚本路径、可写的应用状态目录；每次事件调用脚本会有少量开销，失败或超时可能影响交互。安装前备份原有 `hooks.json` 和目录绑定，保留其他Hook，输出备份路径。恢复时只还原本产品管理的配置，避免覆盖后来新增的其他Hook；升级后检查路径、信任和真实事件。引导不安装系统自启，也不把安装视为任务执行授权。

以上增强引导与检测从 0.1.0-rc.4 起提供；较早版本使用分步安装和手动核验流程。

## 自动注册与黑名单

`pm-server project request` 校验给定项目后立即注册；PM Skill 经理初始化调用同一公共 CLI。重复调用按 CSV 真实路径去重，不扫描磁盘、不启动服务。

在**设置 → 项目管理**中移除项目，即加入持久**黑名单**。普通请求与旧版 `--auto` 请求均不能使它重新加入，重启后也保持屏蔽。移除会断开工作台访问与后续监测，不删除项目文件或会话。**恢复连接**立即恢复并保留项目 ID；**取消屏蔽**只清除黑名单记录，允许下次请求自动加入；在设置中主动添加该项目也可恢复。

工作台启动时会重新校验旧版待确认连接，有效项目直接加入；无效来源保留在**连接待重试**中，显示错误并提供重试操作。旧版移除记录继续作为黑名单。注册不等于经理接管或任务执行授权。旧版 Server 可能仍返回 `pending`，需使用该版本的确认流程或升级 Server。

## 平台接入

```sh
pm-server adapter list
pm-server adapter install codex --dry-run
pm-server adapter check codex
```

历史 Codex 安装器可通过 `adapter install codex` 调用：合并用户配置并保留备份，仍需在目标宿主核实事件和信任机制。配置检查通过只证明文件配置，不证明真实事件触发。不要将此操作用于未确认支持该 Hook 格式的宿主版本。

DSH 配置指向安装包内 `adapters/dsh/observer.js`，只使用 Cordis `apply(ctx)` 和三个 `agent/*` 事件。加载标记按实例分开；宿主重载方式由实际版本决定。详见适配器说明。直接引用 npm 安装目录时，升级后须核验引用仍然有效。

### 标准事件

```sh
printf '%s\n' '{"session_id":"session-1","status":"running","turn_id":"turn-1","event_id":"event-1"}' \
  | pm-server event ingest --host claude-code --instance main
```

状态支持 `idle/running/waiting/interrupted/ended/unknown`。未知状态按未知处理。新接入使用 `host:instance:session` 的编码引用；项目中的会话路由必须使用相同引用，不能把不同平台的同名原生 ID 混在一起。

有事件时间、顺序号时传入 `occurred_at`、`sequence`；没有可靠顺序证据时不把迟到的终态视为新轮次的结束。当前事件入口直接进行串行原子提交，返回成功表示已经落盘；没有离线事件收件箱或无限重试承诺。

`CODEX_SESSION_RUNTIME_CSV` 仅为历史单宿主 CSV 桥接。显式设置后，历史 Hook/DSH 写入保持原生 ID，不能将这种桥接配置当成多宿主身份隔离。新安装使用应用默认路径和完整引用。

## 配置提醒

默认不向 AI 会话自动发消息。明确配置已验证后端：

```sh
export PROJECT_MANAGER_NOTIFY_BIN=/absolute/path/to/notifier
export PROJECT_MANAGER_NOTIFY_ARGS='["--to","{manager}","--message","{message}"]'
```

`{manager}`、`{message}`、`{kind}` 按字符串参数替换，不通过 shell 执行。后端需要自行识别完整会话引用并路由到对应平台；没有这种能力时保持投递停用。旧 Codex 队列仅在显式设置 `PROJECT_MANAGER_CODEX_BIN` 时启用，真实可用性由目标环境验证。

提醒去重与暂停存储在应用的 `monitor/`，不写项目 `TASKS.csv`、任务卡或日志。投递接受不等于经理处理；超时或崩溃可能产生重复提醒，不承诺 exactly-once。经理作出任务决定后再按 PM Skill 维护账本。

```sh
pm-server monitor pause --repo /project --task ABC-001 \
  --until 2099-01-01T00:00:00Z --reason '等待已约定结果' --actor '项目经理'
pm-server monitor resume --repo /project --task ABC-001 --reason '继续检查' --actor '项目经理'
```

## 开发、验证与发布

```sh
npm test
npm pack --dry-run
```

测试使用临时状态和随机端口，需要回环权限。浏览器回归入口为 `scripts/workbench-browser-test.mjs`，通过 `--output` 和 `--playwright` 指定实际位置。格式读取快照记录在 `contracts/`，本项目不 import PM Skill 源码。

两个项目独立版本，通过 `contracts/protocol.json` 的版本和格式约定配合。两个项目采用 MIT 许可证；npm 发布与 GitHub 推送相互独立，真实平台验证范围见上表。当前候选不包含系统自启管理、原生 Claude Code 自动安装或自动迁移承诺。

## 界面语言

登录页、工作台、设置、分享、通知和任务详情支持英文与简体中文。默认按浏览器首选语言选择：中文环境使用中文，其他环境使用英文；浏览器向网页提供的首选语言通常跟随系统或浏览器设置。可手动切换并记住选择，选择“跟随系统”恢复自动。项目名称、任务内容、作者、依据、路径和 CSV 原始值保留原文。

### 运行观察恢复

工作台基础检查核对项目来源可读性；经理登记/在线、AI宿主登录、Hook信任、观察样本及通知就绪均为独立诊断中的可选能力，不阻止查看任务。默认折叠的运行诊断中可单独检查已登记的活动执行会话，并从可识别的本机 Codex 会话日志恢复观察记录。后台监测使用同一有界适配器，核对会话身份与项目目录，只读取匹配日志的有界片段，并仅将状态、事件时间与观察来源写入私有应用缓存。不启动会话、不改任务真源、不信任 Hook，也不生成 Hook 执行凭据。

日志观察说明记录时刻的会话活动，不能证明任务此刻仍在运行或业务交付已验收。记录缺失、无权限、过期、格式不支持或归属不匹配时保留待核验并说明原因；其他宿主需要对应适配器。安静的非活动会话使用比活动会话更长的观察有效窗口。

经理/会话就绪及执行观察缺口属于能力诊断，不是工作台接入未完成；owner鉴权、分享权限、CSRF和来源隔离继续严格执行。当前缺记录不证明会话历史上未被观察，也不证明迁移成功；这类缺口保留在运行诊断中，不单独触发反复经理通知。已观测后过期、无效以及非活动/中断交接仍保留原提醒规则。明确登记的项目经理优先用于通道检查和提醒，旧任务级经理路由保留，待经理后续在授权内实际协调时按已核实事实收敛；只读状态查询不启动该协调。
