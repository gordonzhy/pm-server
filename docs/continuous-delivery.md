# Continuous delivery to npm

The `check.yml` workflow tests Node 22 and 24 on macOS for pushes and pull requests. Its downstream Ubuntu publishing job runs only for a push to this repository's `main` branch after both test jobs succeed. Publishing requires a matching npm trusted publisher configuration; committing this workflow alone does not enable npm authentication.

The test matrix uses standard macOS Intel runners (`macos-26-intel`). This CI run does not establish ARM64 host validation.

The publisher uses GitHub Actions OIDC, with `contents: read` and `id-token: write` limited to the publishing job. It needs no npm token secret. Configure the npm package `pm-server` to trust GitHub owner `gordonzhy`, repository `pm-server`, workflow file `check.yml`, environment `npm-next`, with direct publish permission. Configure that GitHub environment to allow deployment only from the `main` branch (custom branch policy, no tag rules). The branch restriction is part of the security boundary; a workflow condition alone is insufficient. Do not enable unrelated actions or change account-wide authentication settings. The workflow uses GitHub-hosted runners, Node 24 and npm 11.16.0. See [npm trusted publishing](https://docs.npmjs.com/trusted-publishers/).

New npm trusted publisher configurations always include staged publishing. Enabling direct publishing therefore results in `createPackage` and `createStagedPackage` permissions within this same package and workflow scope. Do not grant `manageDistTags`. This workflow only publishes directly to `next`; it does not submit or approve staged packages. A staged submission still requires a maintainer's review and 2FA approval to become public. The platform's mandatory staging permission cannot be removed from a new direct-publishing configuration.

Each release has version `<base>-ci.<workflow-run-number>.<first-12-source-SHA-characters>`, for example `0.1.0-ci.123.aaaaaaaaaaaa`. The base is the numeric version in `package.json`. The package's `releaseSource` records the full public source SHA and run number. Version changes occur only in the runner checkout; no version commit or release tag is pushed back to GitHub. npm provenance records the public repository and build identity.

Publishing always targets `next`; it does not promote `latest`. A package-wide concurrency group serializes publishing jobs. Before publication the job checks that the source is still `main` and that `next` is not from a newer run. GitHub may replace pending concurrency jobs; superseded pushes can be skipped. A newer push arriving after the final head check can briefly leave the preceding release on `next` until its successor succeeds. A failing or superseded run does not promise a release.

The release script verifies an explicit archive file list, required licenses, source/archive byte equality, package metadata and generic privacy indicators. These checks complement human review of source, images and dynamic outputs; they cannot establish that arbitrary instance data is safe to publish. Review any change to the archive allowlist deliberately. Immediately before publishing, it repacks and verifies the exact candidate integrity. It publishes the directory to avoid tarball-origin absolute path metadata; npm must upload the same tested archive bytes. After publishing it anonymously downloads the exact registry archive, checks its integrity, normally installs it into a temporary prefix, compares the installed files and runs CLI help. No local service or global installation is changed.

Rerunning the same workflow run produces the same version. If that version already exists, its integrity and source must match; the retry does not publish it again or change `next`. A failure with an uncertain publish outcome requires checking the exact registry version first. A matching existing version still goes through anonymous download and installation verification on rerun. The job summary contains candidate and outcome receipts on success. Failed logs remain available in Actions.

After an upload, the publisher allows up to six minutes (at most 36 reads, ten seconds apart, with an absolute time budget) for registry visibility using read-only lookups; it never repeats the upload while waiting. It reads the full package record using npm's documented cache-revalidation query (`GET ?write=true`), checking the selected version and tags from the same response. Source comparison requires exactly the repository, commit and run fields with their original values, regardless of JSON key order. Package dry-run runs only for a new version, so an already-published matching version can recover through verification without a second publish attempt.

To pause automatic publishing, disable this workflow in GitHub Actions or remove this package's specific trusted publisher relationship in npm settings. Disabling the workflow also pauses its tests. To pause only publication while retaining CI, remove or disable its `publish-next` job through a reviewed change. Published versions are immutable; correct defects with a new reviewed push. Moving `next` back to an older reviewed version is an explicit maintainer operation, and must be coordinated with active publishing jobs. It does not affect `latest` or remove existing versions.

If the target is already visible, verification proceeds immediately; otherwise it can take up to six minutes after upload, plus download and installation. This bounded window accommodates observed cache lifetimes; it does not establish the cause of any earlier delay or guarantee visibility. Each read emits only typed target/tag state, HTTP status and approved cache TTL fields. Network, timeout and invalid-JSON failures use fixed categories without response bodies, credentials or raw errors. A timeout fails the job; it never triggers another upload.
